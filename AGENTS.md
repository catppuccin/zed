# Working on Catppuccin for Zed

`AGENTS.md` is the canonical guide; `CLAUDE.md` is a relative symlink to it.
Documentation and the macOS Computer Use workflow were checked on 2026-09-07.
Check current documentation and the installed Zed version when behavior differs.

## Project and commands

- [justfile](justfile) is the source of truth for setup, builds, cleanup, and releases. Read it and run `just --list` before choosing commands. [.zed/tasks.json](.zed/tasks.json) provides editor shortcuts; prefer the recipes when instructions disagree.
- [zed.tera](zed.tera) is the Whiskers/Tera source for theme colors. Edit this template and regenerate; do not hand-edit generated JSON.
- [extension.toml](extension.toml) identifies the `catppuccin` extension. This checkout is already installed in the user's Zed as a dev extension. Keep the build directory and installed dev-extension directory aligned, especially when using another checkout or worktree.
- Each generated theme file contains Latte, Frappé, Macchiato, and Mocha. The matrix generates an italics and a no-italics file per accent. Only `themes/catppuccin-mauve.json` and `themes/catppuccin-no-italics-mauve.json` are currently tracked; other accents are ignored by [.gitignore](.gitignore).

Run recipes from the repository root:

| Command | Purpose |
| --- | --- |
| `just` or `just --list` | Show available recipes. |
| `just setup` | Install Whiskers with Homebrew on macOS, if needed. |
| `just build` | Generate all four flavors, both italics variants, with the default mauve accent. |
| `just build blue` | Generate the same variants with a blue accent. |
| `just all` | Generate the complete accent matrix. |
| `just clean` | Remove generated theme JSON, including tracked files; use only when cleanup is needed and regenerate afterward. |
| `just release <tag>` | Generate all themes, sign and push a tag, and publish release assets. Use for an explicitly requested release. |

The `build` argument is currently named `flavor`, but it overrides **accent**.
For example, `just build blue` is valid; `just build mocha` does not select Mocha.
Use `just --dry-run build blue` to inspect the underlying command.

## Commit and PR titles

All PR titles targeting `main` and all commit subjects landing on `main` must follow
[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/):
`type(scope)!: description`, with the scope and `!` optional.

- Use lowercase types such as `feat`, `fix`, `docs`, `ci`, `build`, `chore`, `refactor`, `perf`, `test`, `style`, or `revert`.
- Use `fix` for theme corrections and `feat` for new capabilities. Reserve `style` for formatting-only changes.
- Examples: `fix(markdown): improve heading contrast`, `feat(syntax): add preprocessor highlighting`, `docs: expand theme debugging guidance`.
- Indicate breaking changes with `!` or a `BREAKING CHANGE:` footer, and explain the impact.
- Before merging, verify both the PR title and the final commit subject. For squash merges, use the validated PR title as the commit subject; if individual commits will land, check every subject. Correct nonconforming titles/messages before merging, including autogenerated merge messages, and preserve any breaking-change footer.

## Catppuccin color reference

The [official palette](https://catppuccin.com/palette/) has one light flavor, Latte,
and three dark flavors: Frappé, Macchiato, and Mocha. All four share 26 color names.
Choose a symbolic color in `zed.tera`, such as `c.blue.hex` or `c[accent].hex`, so Whiskers supplies
each flavor's value. Look up exact values on the palette page instead of maintaining
a second hex table here. When comparing a screenshot or generated JSON, account for
the selected flavor and any template mixing or opacity.

The [palette specifications](https://github.com/catppuccin/catppuccin/blob/main/docs/specs.md)
separate neutral colors commonly used for UI from colorful accents commonly used for
syntax. The [style guide](https://github.com/catppuccin/catppuccin/blob/main/docs/style-guide.md)
gives these starting roles; legibility takes priority:

- **Surfaces:** `base` for the canvas; `mantle`/`crust` for secondary panes; `surface0`–`surface2` for controls; `overlay0`–`overlay2` for overlays.
- **Text:** `text` for body copy; `subtext0`/`subtext1` for secondary labels; `base` on an accent background. Selection backgrounds use `overlay2` at 20–30% opacity.
- **Status:** `green` for success, `yellow` for warnings, `red` for errors; `rosewater` for the cursor.

| Syntax role | Palette color |
| --- | --- |
| Keywords | `mauve` |
| Strings | `green` |
| Numeric values and constants | `peach` |
| Functions/methods; properties such as JSON keys | `blue` |
| User types/classes/interfaces; XML-style attributes | `yellow` |
| Parameters | `maroon` |
| Escapes and regular expressions | `pink` |
| Symbols/atoms; built-in functions | `red` |
| Macros | `rosewater` |
| Operators | `sky` |
| Comments and delimiters | `overlay2` |
| Enum variants | `teal` |

Rainbow headings/brackets follow `red → peach → yellow → green → sapphire → lavender`.
For terminal work, consult the guide's [ANSI mappings and bright-color generation](https://github.com/catppuccin/catppuccin/blob/main/docs/style-guide.md#terminals).

Apply these defaults through Zed's actual capture mapping. Inspect the Highlights
view and relevant maintainer clarifications before changing a rule:
for example, [built-in types are mauve, user types yellow](https://github.com/catppuccin/zed/issues/157#issuecomment-4780605377).
The code-editor guide is still evolving; recheck it for the affected role and explain
any deliberate Zed-specific deviation in the change. Preserve `justfile` as the
authority for how to build and verify this project.

## Diagnose and iterate

1. Read the issue body, comments, linked changes, and relevant screenshots. Record the Zed version, exact theme name, flavor/accent, italics variant, language, and reproduction steps. Check `git status --short` and preserve existing edits and unsaved buffers.
2. Confirm the active theme and dev extension. In `zed: extensions`, search for Catppuccin: the local entry should be marked `(dev)` and the marketplace entry overridden. The theme selector identifies the active variant. Check relevant user/project overrides and light/dark mode if observed colors disagree with generated JSON.
3. Reproduce with a small example and capture the original appearance. For Markdown, distinguish source text, rendered preview, and fenced code: they need separate inspection. For UI controls, reproduce the exact selected, focused, hovered, pressed, or disabled state.
4. For syntax, run `dev: open highlights tree view` to see capture names, theme mappings, and effective colors. Focus the source editor if the view says it is not attached. Use `dev: open syntax tree view` to inspect parsing and injected languages. Determine the capture actually emitted before choosing a theme key; adding a finer-grained key cannot separate tokens that still resolve to the same style. Check semantic highlighting when an LSP supplies different classification.
5. For UI colors, consult the schema and the consuming widget. `element.*` and `ghost_element.*` are shared across controls; check sibling uses before changing one. `*.active` describes a press, while `*.selected` describes a persistent selection/toggle. Evaluate translucent colors over their actual background, and move focus/pointer away when checking the resting state.
6. Change the shared rule in `zed.tera`. Reuse `c.<color>`, `c[accent]`, and existing `mix`, `mod`, `add`, or `sub` patterns. Preserve the `italics` variable where appropriate so the no-italics variant remains effective. Inspect related captures and legacy aliases instead of patching only one generated flavor.
7. Run `just build` (or `just build <accent>` for the variant under test), then execute `zed: reload extensions` in Zed's command palette. If the display stays stale, inspect `zed: open log`; try `workspace: reload` when needed, preserving unsaved work. Editing `.tera` alone does not regenerate JSON, and Zed's extension reload/rebuild does not replace the Whiskers recipe. This sequence is also documented in [README.md](README.md#development).
8. Repeat the original reproduction and capture the result. Check all four flavors for a shared color change, both italics variants for font-style changes, and a non-default accent when changing accent-dependent rules. Restore temporary theme/settings changes and close temporary debug views. Report what was actually checked, with remaining limitations.

Zed's [semantic-token modes](https://zed.dev/docs/semantic-tokens) currently include
`off`, `combined`, and `full`; inspect the user's effective configuration instead of
assuming Tree-sitter alone controls the color. Personal `theme_overrides` can also
mask an extension change. Keep the final repository fix in the template.

## Developer commands and inspection panes

Press **Cmd+Shift+P**, type `dev: open` to discover the available inspectors, then
select the exact command with the arrow keys and Return. The command groups use
their own prefixes: `dev: ...`, `zed: ...`, and `workspace: ...`. Open the source
file and focus its editor before launching a file inspector.

| Command | When and how to use it |
| --- | --- |
| `dev: open highlights tree view` | Inspect the color swatch, source range, capture, and resolved theme rule for the affected token. This is the first stop for a syntax-color bug. |
| `dev: open syntax tree view` | Inspect node names, nesting, ranges, and language selection to determine how the file was parsed. Use these nodes to locate the relevant `highlights.scm` rule. |
| `dev: open theme preview` | Open the active theme's preview tab. **Overview** shows surfaces, text colors, and swatches; **Typography** shows heading and body samples. Scroll through the examples, then verify the actual affected widget too. |
| `dev: open key context view` | Inspect keyboard context when an expected shortcut does not run its action. |
| `dev: open language server logs` | Inspect LSP behavior when semantic highlighting differs from Tree-sitter or fails to update. |
| `dev: open debug adapter logs` | Inspect debugger protocol behavior when reproducing debugger-panel issues. |
| `zed: open log` | Inspect extension-loading or theme-parsing errors after generation/reload. |

These command names are listed in [Zed's action reference](https://zed.dev/docs/all-actions).
Syntax Tree, Highlights, and both Theme Preview sections were exercised in the
installed app; the log and key-context commands above are reference lookups.

### Read the Highlights view

Find the row whose source range covers the problem text. For example, the user's
Markdown screenshot shows `syntax: title.markup → title`: `title.markup` is the
capture and `title` is the theme rule it resolves to. Inspect `"title"` under
`syntax` in `zed.tera` and `themes[].style.syntax.title` in generated JSON. The row's
swatch and any font-style annotation show the resulting appearance. Distinct
captures can resolve to one theme rule; use the mapping shown by this Zed version.

If Highlights says **Not attached to an editor**, click the source editor. Check the
language/range shown by Syntax Tree when changing files; if it still targets the
old file, focus the new source, then use `syntax tree view: use active editor` from
the inspector. Empty or unrelated results call for checking focus, language, and
view filters before changing colors.

### Arrange and use the panes

- Keep the source and the needed inspector visible together; add the second inspector when investigating parsing. Click inside the source to restore editor focus. Widen a pane by dragging its divider and scroll with the pointer over the pane you intend to inspect.
- **Syntax Tree and Highlights are editor panes.** Use the tab's context menu to close a finished inspector. `workspace: activate pane left` / `workspace: activate pane right` move focus, and `workspace: toggle zoom` expands/restores the active pane.
- **Dock panels have separate controls.** Use **View → Project Panel / Outline Panel / Terminal Panel / Debugger Panel** for the named panel. **View → Toggle Left/Right/Bottom Dock**, or the corresponding `workspace: toggle left dock`, `workspace: toggle right dock`, and `workspace: toggle bottom dock` commands, show or hide docks.
- After moving, resizing, or hiding anything through Computer Use, obtain fresh state and a screenshot before choosing the next target. Keep any panes the user already opened; close only temporary views created for the current inspection.

## Control Zed with Computer Use

Use the available native Computer Use tool for UI interaction. In this environment
that is `mcp__cua_repl.js`; its returned runtime documentation is authoritative for
API names and permissions. Use shell/file tools for repository work and the GitHub
connector for issues. Zed is a native app, so browser DOM automation does not apply.
If Computer Use is unavailable, say that visual verification is unavailable.

On the first call, or after a runtime reset, execute only this entry-point call and
read the returned documentation/state before making further calls:

```js
let zed = await cua.getApp("Zed");
```

Reuse that binding in the persistent session. If the name fails, call
`cua.listApps()` and retry with Zed's returned bundle ID. Confirm the window/project
before acting. A window's exposed `Raise` secondary action can bring it forward;
use the current element index, never an index copied from this document.

Open the palette and inspect it before typing:

```js
await zed.pressKey("super+shift+p");
await zed.getAXState();
await zed.getScreenshot();
```

Once the palette input is visibly focused, enter the desired action and inspect the
match before executing it. For a theme reload:

```js
await zed.typeText("zed: reload extensions");
await zed.getAXState();
await zed.getScreenshot();
```

After confirming the intended result is selected:

```js
await zed.pressKey("Return");
await zed.getAXState();
await zed.getScreenshot();
```

- **Observe after actions.** Batch deterministic actions with `getAXState()`, then decide the next step from fresh state. Do not build a long blind sequence. Zed's [command palette](https://zed.dev/docs/command-palette) uses Cmd+Shift+P on macOS (`super` means Command in this runtime).
- **Use screenshots for missing UI and color.** In the tested Zed session, the accessibility tree exposed the window and menu bar but omitted the editor, palette, extension cards, and debug panes. An unchanged tree did not mean an action failed. `getScreenshot()` showed the actual state; accessibility text cannot establish color correctness.
- **Ground targets in observations.** Prefer current accessibility indices when available; otherwise click coordinates from the latest screenshot. Re-observe after layout changes. After a screenshot-only observation, request `getAXState({ disableDiffing: true })` before relying on accessibility indices again.
- **Protect editor contents.** Text input goes to the focused control. Verify focus before `typeText` or `paste`; use `paste` for multiline samples. Create a scratch example or edit files with repository tools instead of blindly typing into the user's buffer.
- **Recover visibly.** Dismiss a palette with Escape and verify it closed. If a native menu ignores Escape, use `performSecondaryAction(index, "Cancel")` only when that action is exposed. In this session Cmd+W did not close debug tabs; their tab context menu's `Close` action did. Verify the close and use fresh coordinates for the next tab.
- **Verify outcomes.** A command sent is not a successful reload or fix. Check the target UI and the original reproduction. Theme-selector navigation previews colors; Return saves the selection, so preserve the original theme when comparing variants. See [Zed themes](https://zed.dev/docs/themes).

The general observation/action/verification approach is covered by
[OpenAI's Computer Use guide](https://developers.openai.com/api/docs/guides/tools-computer-use).
Its API integration examples are separate from this session's `cua_repl` API;
use the installed tool rather than implementing another automation runtime.

## Verify a theme change

Regenerate through `justfile` and inspect the diff. There is currently no `just check`
or `just test` recipe. The following direct Whiskers check uses the mauve override
from [.github/workflows/check.yml](.github/workflows/check.yml); prefer a recipe if
one is added later:

```sh
whiskers zed.tera --overrides '{"accent": ["mauve"]}' --check
python3 -m json.tool themes/catppuccin-mauve.json >/dev/null
python3 -m json.tool themes/catppuccin-no-italics-mauve.json >/dev/null
git diff --check
git diff --stat
```

`--check` verifies template/output consistency; JSON parsing verifies syntax.
Neither proves that Zed uses a key or that a visual issue is fixed. Confirm changed
fields against the schema/current source and complete the in-app reproduction.
Include template changes and regenerated tracked themes together; keep temporary
samples and screenshots out of the patch unless requested.
